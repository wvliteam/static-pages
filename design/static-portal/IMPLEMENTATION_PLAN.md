## 2. SP-00：基线、范围和版本准备

### 工作内容

1. 读取 README、AGENTS、当前分支、远端和未提交修改，确认可复用工作分支或隔离检出。
2. 固定本次正式 main 基线，保存 `docs/` 文件清单与哈希到忽略的 scratch。
3. 复核历史报告路径与哈希；本设计基线报告 SHA-256 为 `e7fbd1ecd16e6395a07adf1d6026ef3b81d5d8f6a1bc6d739a7227ab8867ddc2`。
4. 检查拟议目录是否已被其他内容占用。有同名页面时先理解用途与兼容要求，不以新设计自动覆盖。
5. 核对 Personal 固定来源、Bootstrap bundle 和许可清单，确定沿用实测版本还是单独升级。
6. 选择真实实施任务 `static-portal`。沿用适合的预览分支或按仓库规则准备新分支，不逐页建仓库。

### 完成条件

- 有明确 main SHA、源文件清单、受保护内容与门户写入范围。
- 当前未提交的总计划、研究文档和比较产物均得到保留。
- 首版四个门户页面的路径、资源前缀、导航和数量口径一致。
- 所选依赖有明确版本和来源；没有用“最新”替代版本身份。

## 3. SP-10：门户页面与真实内容

### 文件范围

候选位置为 `artifacts/static-portal/public/` 下的：

- `index.html`。
- `pages/reports/index.html`。
- `pages/tools/index.html`。
- `pages/about/index.html`。

### 工作内容

- 复用已验证 Personal 布局，替换为实际站点内容；不复用研究文章或虚构个人资料。
- 顶部导航统一为首页、报告、工具、关于，按各页深度写相对链接。
- 报告目录明确链接当前正式历史报告，日期与标题使用已有内容。
- 工具目录当前使用真实空状态；不制造可用工具数量和占位入口。
- 关于页说明独立页面、历史快照、内容日期、模板来源和仓库入口。
- 首页只展示正式内容；必要数量按内容类别统计，不把导航页面计为报告或工具。

### 完成条件

- 四页均具有非空 title、viewport、语义主区、可见焦点和有效导航。
- 无测试文章、默认人物、联系表单 token、假链接或模板占位。
- 历史报告内容未修改，新增入口能解析到正确路径。
- 入口页布局仍以内容阅读为目的，实际文案与视觉在后续预览中审阅。

## 4. SP-20：本地资源与来源管理

### 文件范围

- 候选中的 `assets/portal/`、`licenses/portal/`。
- 根目录维护资料 `third_party/portal/UPSTREAM.md`，实施时新增。

### 工作内容

- 将必要第三方样式、Bootstrap bundle、favicon 放入独立命名空间。
- 系统字体回退和小范围自有样式放在 `portal.css`；不修改报告样式。
- 去除未使用的外部字体、图标 CSS、SB Forms、示例人像、空扩展脚本。
- 保留版权头、相关许可证和模板来源入口。
- 记录固定提交、依赖版本、文件映射、自有适配及升级方法。

### 完成条件

- 门户渲染与手机导航不依赖第三方 CDN 或外部表单服务。
- 没有将源码归档、构建工具、原始日志或截图复制进 public。
- CSS 的间接资源路径也能解析；不只检查 HTML 的 src/href。
- 文件集合与 SP-10 约定路径匹配，依赖版本与许可齐全。

## 5. SP-30：完整候选与本地验收

### 工作内容

1. 将 SP-00 的正式静态内容快照放入候选根，排除 `.nojekyll` 等明确由部署负责且不适用于预览的控制文件。
2. 覆盖或加入本次门户文件，形成完整可浏览候选。
3. 保存三类清单：门户受管文件、只供预览的正式内容副本、部署控制文件。
4. 使用现有 HTML 检查器检查全部候选 HTML；分别挂载到正式和嵌套路径，使用同一套干净文件验证。
5. 验证报告字节未变、全体本地资源可访问、菜单和主要导航可操作。
6. 做手机和桌面截图回读；至少检查 375、768、1440 宽度及实际键盘导航。
7. 初步形成未来收录清单，仅列门户受管文件及必要维护资料，不将完整快照视为整体覆盖命令。

### 完成条件

- 正确路径下静态检查通过；原报告哈希保持基线值。
- 没有因换 base 修改候选字节；没有手写部署横幅或 `data-static-preview`。
- 受管文件和镜像文件可区分，未来的覆盖与保留范围明确。
- 已执行、失败、未执行的检查如实记录，问题修正后重新回读。

实施时的检查方式见 [验收说明](ACCEPTANCE.md)。本轮文档不假设候选页面已经存在。

## 6. SP-40：发布兼容性与最小 CI

### 工作内容

- 根据实际仓库状态重查 Pages 来源、部署环境和事件策略。此前 R01 的调查与时间节点作为核查线索，不能当作本次配置结论。
- 优先维持现有可信 main 组合静态文件的边界。确需调整事件入口时，按 R01 备选路线单独实施、验收和记录。
- 增加独立低权限候选检查，使用事件对应的明确候选版本，执行适用静态检查与相关测试。
- 单独表达 main 合并就绪：任何指向 main 的候选合并树均不得含跟踪的 artifacts。
- 先验证固定检查名及结果，再按实际仓库规则配置必要的合并要求。

### 完成条件

- 能发现真实候选缺陷；不是只重复 main 上的旧测试。
- 预览有效、尚不可合并的状态能正确呈现，不因此取消正常预览。
- 发布权限没有进入候选代码或浏览器执行环境。
- 打开、更新、关闭与资格变化的预览生命周期有明确的重建或兜底路径。
- 不能仅以上游 success 作为接收预览调度信号的条件。

### 范围控制

本工作包可以作为独立基础设施维护 PR，与门户页面并行。修改代码或工作流时运行相关测试，不为仅文档变更增加测试代码。不强制先实现通用 promotion CLI、MCP 服务或所有 skill 配套。

参考：[R01 研究](../../research/2026-11-21-priority-implementation/R01-actions-event-compatibility.md)、[R02 研究](../../research/2026-11-21-priority-implementation/R02-pr-validation-ci.md)。

## 7. SP-50：实际在线预览与版本确认

### 工作内容

1. 在预览分支只显式暂存当前任务所需静态文件和维护改动，不将三个比较样例一起暂存。
2. 创建或复用同仓库、base=main 的实际 PR，等待对应可信工作流。
3. 从成功运行摘要及 manifest 获取真实预览 URL，核对 PR head SHA 与任务文件哈希。
4. 打开真实预览，复查四个门户页面、报告目录、原报告及工具空状态。
5. 记录用户确认的具体预览 SHA、干净源文件清单和检查证据。
6. 核对该 SHA 实际 GitHub 归档中被选择的干净字节与记录一致；若存在归档导出或 checkout 变换，明确停止比较并修复，不做文本归一化绕过。

### 完成条件

- 有可直达的真实预览，源版本和文件内容均已核验。
- 预览内导航、资源和旧报告正常；正式首页仍保持原状态。
- 用户对具体页面版本的确认已经具备，或本会话已有可复用的同版本授权。
- 技术路线采纳、CI 通过、截图通过均没有被误作具体门户版本批准。

预览后实质内容变化，按既有规则提供对应版本复核；相同产出已有有效授权时，不重复申请。

## 8. SP-60：受控收录、部署与核验

### 工作内容

- 固定 SP-50 确认 SHA，读取实际干净输入及逐文件哈希。
- 重新检查当前 main 相对预览基线的变更，识别门户冲突与需要刷新的依赖。
- 仅应用门户受管文件增量；不将旧完整快照覆盖到正式 docs。
- 核对所有历史报告、工具和无关文件保留；需要删除的旧门户资源逐项确认没有引用。
- 更新正式 README、导航与数量，移除本次已跟踪的 artifacts；最终候选不得含任何跟踪草稿。
- 检查完整 diff 和适用检查结果，再按既有授权和仓库规则合并。
- 等待本次部署成功，记录真实 main SHA、运行 URL、manifest 与验证结果。
- 正式 HTML 使用现有验证器；门户非 HTML 资源逐项核对线上哈希和本地字节。

### 完成条件

- 门户正式文件能追溯到确认版本，路径映射和字节一致。
- 旧报告地址及哈希保持原值，新进入 main 的无关内容没有丢失。
- main 无 tracked artifacts；没有手工编辑 gh-pages 或保留部署路径。
- 真实交付 URL、明确 main SHA 与线上文件匹配；不是只看到 HTTP 200 或生成分支更新。
- 所有未完成的浏览器或平台验收事项单列，不隐含为通过。

## 9. SP-70：维护说明和交接

### 工作内容

- 将新增报告、工具、普通页面的操作步骤更新到实际维护指南。
- 给两个 skill 增加必要的门户交接说明，保持各自独立职责，不复制仓库全部规则。
- 记录导航变更需要同步四页、目录数量口径、第三方升级和回退方法。
- skill 真有修改且需要使用时，再同步安装副本，先保护本机修改。
- 将比较样例与正式产物区分；保留用户或其他任务文件，不能全局清理整个 artifacts／scratch。

### 完成条件

- 新增下一份真实报告只需维护明确的内容与入口，不依赖个人对话记忆。
- 新维护者能找到正式源、许可、来源记录和检查方式。
- 页面回退与基础设施回退可以分别进行。
- 长期命令以使用指南和实际脚本为准，设计文件不演变为另一份重复操作手册。

## 10. 并行方式、PR 切分和里程碑

### 可并行部分

| 工作 | 可并行关系 | 文件责任边界 |
| --- | --- | --- |
| SP-10 内容 | 可与 SP-20、SP-40 并行 | 四个门户 HTML |
| SP-20 资源 | 可与 SP-10、SP-40 并行 | assets、licenses、来源记录 |
| SP-40 基础设施 | 可与页面和资源实现并行 | workflows、检查入口、相关 tests |
| SP-30 验收 | 等待页面与资源稳定；之后可分静态和浏览器 | 检查默认只读，问题回到各自责任范围 |
| SP-50／SP-60 | 版本确认与正式发布顺序执行 | 同一发布负责人固定版本与迁移清单 |

共享导航路径和资源文件名先固定，再并行编辑。默认不让多个执行者同时改同一份 HTML、索引或发布分支。

### 建议 PR

1. **维护 PR：发布兼容性与候选检查。** 对应 SP-40；按维护授权执行，不套用新增页面正式收录审批。
2. **门户预览 PR：实现、资源、本地验收与在线审阅。** 对应 SP-00～SP-30、SP-50。确认后在同一 PR 做受控收录提交，进入 SP-60。
3. **必要的维护收敛提交或 PR。** 完成 SP-70 中不影响已审阅页面的说明；与页面有关的实质变更按当前规则再核对。

里程碑为：M0 基线与路径明确；M1 完整候选通过本地检查；M2 真实预览及确认版本可追溯；M3 正式 URL 与字节验收通过；M4 维护交接完成。

当前完成的是技术路线采纳和本文档编制，不将 M1～M4 标记为已完成，也不预设未经评估的工期。
