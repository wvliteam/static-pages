# candidate-validation Specification

## Purpose

让维护者在审阅拉取请求时看到候选代码和静态文件的检查结果，也能判断提交是否仍含待审阅的草稿。结果对应可追溯的 Git 提交，并与线上预览、用户确认和正式发布流程分别记录。

## Requirements

### Requirement: 独立报告候选质量和合并就绪

目标为 main 的 PR MUST 分别报告候选验证及合并就绪；合并就绪 MUST 检查完整测试合并树中的草稿文件。

#### Scenario: 预览产物有效但仍在审阅

- **WHEN** PR head 含可用的预览文件，且测试合并树仍跟踪 artifacts 中的文件
- **THEN** 在其他检查均通过时，候选检查通过，合并就绪检查失败并指出草稿路径

#### Scenario: 迁移完成后无草稿

- **WHEN** 测试合并树不含跟踪的 artifacts 文件
- **THEN** 草稿隔离条件通过，结果不取决于分支名或工作区中未跟踪的文件

### Requirement: 验证固定版本的页面及其直接依赖

候选验证 MUST 测试候选合并提交的代码和正式 HTML，并按 PR head 检查预览归档；记录事件 base、PR head 及实际测试提交。

#### Scenario: 预览文件不符合发布输入

- **WHEN** 预览缺入口、HTML 结构无效、引用的本地文件缺失，或预览文件在归档时被移除或改写
- **THEN** 候选检查失败并说明原因

#### Scenario: 正式页面引用的直接资源被删除

- **WHEN** 测试合并树的正式目录删除其他页面直接引用的资源
- **THEN** 候选检查失败并指出受影响的正式 HTML

#### Scenario: 无法取得事件指定的测试版本

- **WHEN** 对应 Git 对象缺失或提交版本关系不符
- **THEN** 检查失败，不改用当前分支最新版本

### Requirement: 隔离候选运行和部署权限

候选运行 MUST 使用独立的低权限 PR 工作流，不给候选步骤提供发布凭据或把检查结论视为发布授权。

#### Scenario: 合并就绪失败时审阅页面

- **WHEN** 仍含草稿的有效预览 PR 运行候选检查
- **THEN** 可信 Pages 工作流仍按原规则处理该预览，不等待候选工作流的整体成功
