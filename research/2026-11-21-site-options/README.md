# 现成静态站点方案：最小接入对比

- 对比日期：2026-11-21。
- 仓库基线：`ee180b1e36d71b600f324ddbaa8d64e493862565`。
- 本地工作分支：`preview/site-options-comparison`。
- 状态：三条路线均完成真实本地产物、路径验证和基础浏览器检查；尚未选为正式站点，也没有上传或部署。
- 本轮目标：验证能复用多少现成功能、已有报告能否保留，以及与当前发布约定的接入成本。

## 1. 结论先行

三种现成项目都能够承载既有独立 HTML 报告，并保留原相对 URL 和文件字节。差异主要在内容写作方式与发布约定，而非能否运行在 GitHub Pages。

推荐按实际主线选择：

1. **持续以 Markdown 写博客、需要自动文章归档：优先 PaperMod。** 本次用一个固定 Hugo 二进制即可构建，样例没有引入 Ruby 或 Node 构建依赖，文章、标签、归档和订阅可复用。需要明确正式与预览 base 之间的构建和确认方式。
2. **保持当前独立报告／工具为主，只增加一个入口首页：优先直接静态 Personal。** 无生成器构建，同一份产物通过两种路径挂载验证，与当前静态字节交付最接近。代价是新增文章及列表仍需人工维护。
3. **需要 Jekyll 的页面／内容集合组织，或已有 Ruby 工作流：保留 Minimal Mistakes。** 本次文章、归档与搜索可用，但需要 Ruby/Jekyll，且同样面临 base 重建成本；当前默认图标还依赖外部 CSS。

如果目标是普通个人博客，应先确定成熟生成器与常规发布方式，再决定哪些自定义预览功能确实需要。此前 R01–R04 研究仍可作为按需采用的方案，不宜据此默认全部实现。

- 沿用项目品牌“页面集”，不填写未提供的用户姓名、头像、简历或联系方式。

- 使用同一现有 HTML 检查器，并以同一无头 Chromium 做有限的实际行为验证。

不同主题的默认首页目的不同：PaperMod 使用 Profile 布局；Minimal Mistakes 展示报告和文章列表；Personal 复用个人展示式首页。因此本次比较功能与接入成本，不把首页长短或产物大小直接解释成审美、访问速度排名。

## 5. 关键发现：成熟主题减少了什么，又增加了什么

### 5.1 可以直接减少的工作

采用生成器主题，可以复用文章列表、内容布局、标签、归档、RSS／feed 与 sitemap。新增第二篇文章的真实构建已经验证这部分自动更新，不需要先自建一个博客生成器。

直接静态模板则复用了首页、导航、卡片、按钮和响应式布局。对目前独立 HTML 为主的内容，能够在不增加站点生成器的情况下提供入口。

### 5.2 raw HTML 报告仍需要目录信息

原报告作为静态文件复制不会自动变成主题文章。这有助于保留数据、交互和原始字节，但报告的标题、日期与入口仍需至少一处数据或目录条目。

因此，R08 中“自动目录”的一部分可以由主题承担，独立报告目录和 README 正式列表的同步仍需单独决定。不要把 Markdown 文章自动归档扩大解释为任意 HTML 都自动完成收录。

### 5.3 生成器与当前原样迁移约定存在实际摩擦

当前流程要求确认预览中的干净产物，再将其原样迁到正式目录。两种生成器按 base 重建，会改变导航、文章链接、搜索数据、feed 或 sitemap 等文件。

它们分别构建后都能正常运行，但这不等于同一份已确认字节直接迁移。PaperMod 的 `relativeURLs=true` 也进行了实际负例验证，本次不能作为通用解决办法。

如果采用生成器，应在实施前选择明确方式：

- 保持当前原样交付要求，另行验证可移植产物策略及所有导航、资源和元数据；本次没有得到可直接推广的生成器配置。
- 明确将审阅对象扩展为固定源码、工具链、配置和受控 base 变换，并审查两套产物差异。此方案需要修改相关约定，不能静默沿用旧授权结论。
- 如果最终需求允许，采用常规的固定源码构建与发布方式，重新评估多 PR 预览和迁移机制的必要范围。

以上是后续架构选项，本轮没有改变仓库现有确认和发布规则。

## 7. 推荐采用方式

### 场景 A：继续以独立报告和工具为主

采用 Personal 作为可调整的门户起点，以较少构建依赖接入现有流程。保留独立报告原路径；普通文章少量增加时，接受明确的手工列表成本。

正式采用前还应审阅首页内容与视觉，并核对所选静态依赖版本。当前样例只是能力和接入验证，不能直接作为已经批准的正式首页。

### 场景 B：将主要内容转为 Markdown 博客

优先 PaperMod。把站点源码和工具版本作为主要维护对象，利用现成文章能力。同步明确生成器的预览和发布策略，再决定现有发布代码保留多少。

选择 PaperMod 的依据是本次依赖、构建和新增内容实测，以及与项目所需功能的匹配；不是承诺所有 Hugo 场景都不需要其他工具，也不是以一次构建耗时判断整体质量。

### 场景 C：偏好 Jekyll 内容组织

Minimal Mistakes 本次已经真实可用，报告入口和文章列表都能复用。若选择此路线，应固定依赖，评估图标资源本地化／版本固定，并按需要进一步验证中文搜索。统一浏览器中两条中文查询已命中样例文章，但不代表中文分词和检索质量全面通过。
